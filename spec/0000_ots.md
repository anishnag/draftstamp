# opentimestamps-lite

Status: Draft · 2026-11-20

A local OpenTimestamps library (`crates/opentimestamps-lite`, not published). It timestamps a 32-byte digest in Bitcoin through the public calendars and checks the resulting `.ots` proof against Bitcoin. Proofs are standard: the official OpenTimestamps tools read and verify them. It knows nothing about DraftStamp, and is not the upstream [rust-opentimestamps](https://github.com/opentimestamps/rust-opentimestamps) project. "Lite": it evaluates only SHA-256, append and prepend, and trusts only Bitcoin attestations.

## Interface

```rust
impl Proof {
    pub fn from_bytes(bytes: &[u8]) -> Result<Proof, Error>;
    pub fn to_bytes(&self) -> Vec<u8>;
    pub fn digest(&self) -> [u8; 32];
    pub fn status(&self) -> Status;              // offline: Pending | Claimed
}

pub fn stamp(http: &impl Http, digest: [u8; 32]) -> Result<Proof, Error>;
pub fn upgrade(http: &impl Http, proof: &mut Proof) -> Result<Status, Error>;

pub trait Http: Sync {
    fn get(&self, url: &str) -> Result<Response, Error>;
    fn post(&self, url: &str, body: &[u8]) -> Result<Response, Error>;
}
```

| `Status` | Meaning |
| --- | --- |
| `Pending` | No branch reaches Bitcoin yet |
| `Claimed { height }` | The proof names a block, not checked against its header |
| `Anchored { height, time }` | Both explorers agree on the header, and it contains the proof's value |

The library does no I/O; the caller supplies `Http`. Calls are blocking; requests run in parallel on scoped threads. Only `sha256(digest ‖ nonce)` and calendars' own messages ever leave the machine. Dependencies: `sha2`, `getrandom`.

## How it works

**`stamp`:** pick a 16-byte nonce `N`, compute `M = sha256(D ‖ N)`, and `POST M` to the four aggregators. Each reply is a recipe from `M` to a 44-byte calendar message, ending in a pending attestation. Attach the replies under `D → append N → sha256`. At least two must reply within 5 seconds.

**`upgrade`:** for each pending attestation not yet anchored, `GET {calendar}/timestamp/{hex(message)}` (`404` = not yet). Merge each reply below its pending node. Then replay the recipe from `D` to each Bitcoin attestation; the result must equal the Merkle root in that block's header, fetched from both explorers.

## Rules

- Merging only adds; pending attestations are never removed.
- Only allowlisted calendars are contacted.
- Proofs (≤ 64 KiB) and replies (≤ 10,000 bytes) are untrusted; parsing never panics.
- A branch needing an op we do not evaluate is unverifiable, never valid.
- A header both explorers agree on that contradicts every claim is `Error::HeaderMismatch`.

## Format

Defined by the official implementation ([python-opentimestamps](https://github.com/opentimestamps/python-opentimestamps), [opentimestamps-server](https://github.com/opentimestamps/opentimestamps-server)); checked against its source and the live servers on 2026-11-20.

```
magic    00 "OpenTimestamps" 00 00 "Proof" 00 bf 89 e2 e8 84 e8 92 94
version  01
hash op  08 (SHA-256)
digest   32 bytes
tree     from the digest; no trailing bytes
```

`varuint` is unsigned LEB128 (≤ 9 bytes); `varbytes` is a `varuint` length then bytes. A tree node holds attestations and ops, each sorted; every item but the node's last is preceded by `0xff`; an attestation is `0x00` + tag + `varbytes` payload; an op is its tag (plus `varbytes` argument) then its child. At most 256 levels; messages ≤ 4096 bytes.

| Op | Tag | |
| --- | --- | --- |
| SHA-256 | `08` | evaluated |
| append, prepend | `f0`, `f1` + argument (1–4096 bytes) | evaluated |
| SHA-1, RIPEMD-160, Keccak-256, reverse, hexlify | `02`, `03`, `67`, `f2`, `f3` | preserved |

| Attestation | Tag | Payload |
| --- | --- | --- |
| Bitcoin | `0588960d73d71901` | varuint height |
| Pending | `83dfe30d2ef90c8e` | calendar URI |
| Other | any | preserved, never trusted |

Ops sort by tag, then argument; attestations by tag, then height or URI.

| Servers (HTTPS) | |
| --- | --- |
| Aggregators: `POST /digest` | `a.pool.opentimestamps.org`, `b.pool.opentimestamps.org`, `a.pool.eternitywall.com`, `ots.btc.catallaxy.com` |
| Calendars: `GET /timestamp/{hex}` (allowlist) | `*.calendar.opentimestamps.org`, `*.calendar.eternitywall.com`, `*.calendar.catallaxy.com` |
| Explorers: `GET /block-height/{h}`, then `/block/{hash}/header` | `blockstream.info/api`, `mempool.space/api` |

A calendar's pending message is a 4-byte time, the 32-byte batch root and an 8-byte MAC: 44 bytes. A Bitcoin attestation holds when its message equals header bytes 36–67; the block time is bytes 68–71, little-endian.

## Tests

All offline: recorded aggregator replies round-trip byte for byte; the full lifecycle and failure cases run on a simulated network; header checks use the genesis block; truncated and bit-flipped input never panics.

Still to confirm, with a one-time live recording and approval: an anchored proof end to end, and compatibility with the official `ots` client.
